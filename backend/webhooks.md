# Booking Ingestion & Webhooks (Phase 6)

How GQ receives OTA bookings from Channex and creates/updates/cancels them in BQ.

```
OTA (Booking.com, etc.)
  -> Channex
    -> POST /api/gq/webhooks/channex   (live, primary path)
    -> GET /booking_revisions/feed     (recovery, ~every 15 min, catches anything missed)
  -> GQ: resolve property/room/rate mapping, check idempotency
  -> BQ booking API (create / modify / cancel)
  -> GQ verifies the booking via BQ API
  -> GQ acknowledges the revision back to Channex (only after durable success)
```

Both the webhook and the recovery script call the **exact same**
`processRevision()` in `src/modules/booking/booking.service.ts` - nothing is
duplicated between the live and recovery paths.

## One-time setup (required before anything can be received)

1. **Create a `gq_account_config` row via the admin API** (`POST
   /api/gq/account-config`, requires a GQ token with the `admin` role) - there
   are none yet, so every webhook call is rejected with `401
   WEBHOOK_UNAUTHORIZED` until at least one active row exists:
   ```bash
   TOKEN=$(node scripts/mint-test-token.js 1)   # roles: ["Super_Admin"]
   curl -s -X POST http://localhost:4000/api/gq/account-config \
     -H "Authorization: Bearer $TOKEN" -H "Content-Type: application/json" \
     -d '{"webhookUrl":"https://<your-public-host>/api/gq/webhooks/channex","apiKey":"<channex-api-key>","environment":"production"}'
   ```
   The response's `webhookSecret` is shown **once** here and never again -
   `GET /account-config` redacts it on every later read, so copy it now.
   The secret itself is generated server-side (random, not caller-supplied),
   so it can't accidentally be weak or guessable.

2. **Register the webhook with Channex**, `POST {CHANNEX_BASE_URL}/webhooks`:
   ```json
   {
     "webhook": {
       "callback_url": "https://<your-public-host>/api/gq/webhooks/channex",
       "event_mask": "*",
       "is_active": true,
       "send_data": true,
       "headers": { "x-channex-webhook-secret": "<webhookSecret from step 1>" }
     }
   }
   ```
   Channex has **no cryptographic signature scheme** for webhooks (confirmed
   directly from their own docs) - this shared-secret header comparison is
   the complete, real verification available, not a limitation of this
   implementation.

3. **No public URL yet (local dev)?** Skip the webhook and run the recovery
   poller manually instead - it hits Channex directly, no inbound connectivity
   needed:
   ```bash
   npx ts-node scripts/run-revision-feed.ts
   ```

## Account config API (Super_Admin only)

- `POST /api/gq/account-config` - create a config, generates `webhookSecret`
  server-side (random, 32 bytes hex), returned once in the response.
- `GET /api/gq/account-config` - list configs; `webhookSecret` is always
  redacted here.

Both require the caller's GQ session token to carry BQ's `Super_Admin` role
(`requireAdmin` middleware) - `403 ADMIN_ONLY` otherwise. `roles` is passed
straight through unmodified from BQ's own login response, so this must match
BQ's real role name, not an invented one. This exists so the
secret never has to be typed or generated by hand and inserted directly into
Postgres.

## API

### `POST /api/gq/webhooks/channex`
- **Public. No GQ session token.** Verified by the `x-channex-webhook-secret`
  header instead.
- Responds `200 {"received": true}` immediately after the secret check passes.
- Processes the revision **after** responding (fire-and-forget within the same
  process - not a queue, per this phase's explicit scope exclusion).
- A webhook payload only ever carries `{event, payload: {booking_id,
  property_id, revision_id}}` - no room/rate/amount/guest detail. The handler
  always follows up with `GET /bookings/:id` on Channex to get the real
  content before processing.

### Booking / revision read APIs (property-scoped, normal GQ session)

Mirrors Channex's own read-only [Bookings Collection
API](https://docs.channex.io/api-v.1-documentation/bookings-collection) -
Channex's collection there is list/get only too (no create/update/delete on
it; bookings are only ever created by pushing/receiving a real OTA
reservation). GQ does the same: these never write anything, only
`processRevision()` (ingestion) does.

- `GET /properties/:propertyId/bookings` - list `gq_ota_booking` rows
  (optional `status` filter: `new`/`modified`/`cancelled`).
- `GET /properties/:propertyId/bookings/:bookingId` - one booking with its
  full `gq_ota_booking_revision` history embedded, newest first.
- `GET /properties/:propertyId/booking-revisions` - revisions across every
  booking on the property (optional `ackStatus` filter: `pending`/`acked`) -
  the fastest way to find stuck ones (`processingAttempts`,
  `blockingReason`) without knowing a booking's id up front.
- `GET /properties/:propertyId/booking-revisions/:revisionId` - one
  revision.

All four require a normal `authenticate`d GQ session (not `Super_Admin`) and
are scoped to the caller's own `propertyId` - a mismatch between the URL's
`propertyId` and the resource's actual property returns `404` (not `403`),
same as the rest of the app's property-scoped routes.

## Idempotency

Two layers, both required:

1. **Revision-level** - `gq_ota_booking_revision.cx_revision_id` is unique.
   An already-`acked` revision is a pure no-op on reprocessing (used by both
   the webhook and the recovery feed, which will see the same revision again
   and again until it's acked).
2. **Booking-level** - `gq_ota_booking.bq_bookingid` is checked *before* ever
   calling BQ's create endpoint. A retried "new" revision whose booking was
   already created just re-acks, it never creates a second BQ booking - this
   matters because BQ's own API has no idempotency key of its own.

**Real bug found and fixed (2026-10-01): every webhook-triggered ack was
failing with a 404.** `GET /bookings/:id` (the webhook path - `getChannexBooking()`
in `channex.client.ts`) returns `attributes.id` as the **booking's** id, not the
revision's - the real revision id is a separate `attributes.revision_id` field.
GQ was using `attributes.id` everywhere as if it were the revision id (correct
for `GET /booking_revisions/feed`, where `id` genuinely is the revision id -
the recovery poller was never affected). The result: `POST
/booking_revisions/:id/ack` always 404'd (`resource_not_found`) for every
revision that arrived via the live webhook, even though the underlying BQ
booking was created successfully - confirmed directly from a real failed ack
captured in `gq_api_log` (the request/response-capturing API logger built the
same day this was found - without it, only the generic `"Channex rejected the
request."` message would have been visible, not Channex's real
`resource_not_found` reason).

Consequence: the local `gq_ota_booking_revision` row was still correctly
marked `ack_status: "acked"` (that write happens *before* the ack call), so no
duplicate BQ booking was ever created - but the row was left with a
permanently stale `blocking_reason` from the failed ack, and because GQ's own
idempotency check (`ack_status === "acked"`) short-circuits reprocessing, the
*next* time the recovery poller saw the same revision (now carrying the real,
different id from the feed), it created a **second**, separate
`gq_ota_booking_revision` row for the same real-world event - correctly acked
this time, but duplicated in the UI.

Fixed in `getChannexBooking()`: a `normalizeBookingDetailResponse()` step
replaces `attributes.id` with `attributes.revision_id` when the two differ,
so every caller (`processRevision()` included) can keep treating `.id` as
"the true revision id" regardless of which endpoint it came from - unit
tested (`channex.client.test.ts`). Three pre-existing duplicate rows caused
by this bug were identified (each had already been superseded by a correct
sibling row created by the recovery poller) and deleted directly.

## Mapping resolution

For every room in a revision:

```
Channex room_type_id  -> BQ roomtype.cx_room_type_id   (property-scoped)
Channex rate_plan_id  -> GQ gq_rate_plan.cx_rate_plan_id
```

**Both** must resolve or the entire revision is blocked - "do not create an
incorrect booking" is enforced by construction, not by a best-effort guess.
Rooms are grouped by resolved BQ room type name, since BQ's booking-creation
endpoint takes one room type + a quantity per call, not a mixed cart. A
revision spanning more than one distinct room type only creates a booking for
the first resolved group today (documented gap, not silently handled).

Either id can be `null` on the real API - confirmed on a real "Unmapped
Rate" Channex-side booking (Channex's own dashboard shows a red "Unmapped
Rate" badge and an "unresolved issue" banner for it directly - this is
Channex/Booking.com failing to resolve the OTA's room to *any* mapping on
that channel, not a GQ-side failure). `resolveRoomGroups()` checks for a
null id and treats it as immediately unresolved *before* querying the DB -
an earlier version passed a null `rate_plan_id` straight into
`findRatePlanByCxId()`, which crashed (Prisma's `findUnique()` throws on a
literal `null` for a unique column, it does not return "not found") instead
of blocking the revision cleanly. Found by testing against this exact real
booking; fixed, and now blocks with a clear
`{cxRoomTypeId, cxRatePlanId, roomTypeResolved, ratePlanResolved}` reason
instead. **This is the actual fix for "the booking isn't showing up in
GQ and Channex says the mapping is unresolved"** - the booking now shows
up (in `GET /properties/:propertyId/bookings` and `/booking-revisions`)
with `blockingReason` explaining exactly which id didn't resolve, rather
than the revision-feed script crashing before it could even persist
anything.

## The BQ change

BQ's `POST /create-reservation-online-new/` hardcoded three things that don't
fit an OTA booking:

| Field | Was hardcoded to | Needed for OTA |
|---|---|---|
| `booking_type` | `"Online"` | `"OTA"` |
| `booking_status` | `"Soft"` | `"Hard"` |
| final amount | always recalculated from BQ's own price | Channex's actual charged amount |

Fixed with **three new optional fields** on the `Booking` request model
(`booking_type`, `booking_status`, `fixed_amount`) in
`bq/backend/app/api/checkIn/routes/booking.py`. All three default to the
exact original hardcoded behavior when omitted - every existing caller
(walk-in bookings, direct online bookings) is byte-for-byte unaffected.

`booking_status` is constrained by a real Postgres CHECK constraint on
`bq.booking` (`booking_booking_status_check`) to exactly `Soft` / `Hard` /
`Checkedout` / `Cancelled` - there is no `"Confirmed"` value. An earlier pass
of this field used `"Confirmed"`, which is not a real BQ status and made
every OTA booking creation fail with an unhandled `500` (a raw Postgres
constraint violation, since `booking.py` doesn't catch it) - found and fixed
by testing against the live BQ server. `"Hard"` is the correct value for a
guaranteed/confirmed OTA reservation.

`fixed_amount`, when set, overrides the derived pricing totals right before
they're persisted to `billing`/`order_detail`, rather than skipping BQ's own
pricing/discount loop - lower risk, same result.

`POST /modify-booking/` has **no equivalent** override - a modified OTA
booking's amount in BQ may not match Channex's revised amount. Not solved in
this pass, documented here so it isn't forgotten.

## Known limitations

- No cryptographic webhook signature - shared-secret header only (Channex's
  own limitation, not this implementation's).
- `GET /bq/api/bookings/` has no filter params - every verify-after-create
  call fetches *all* bookings and filters client-side.
- BQ matches room types by name only, case-insensitive, with **no property
  scoping** on BQ's side - a pre-existing BQ ambiguity risk if two properties
  ever share a room type name.
- A revision for a Channex property that can't be resolved to any onboarded
  BQ property can't be persisted at all (`gq_ota_booking.bq_property_id` is
  required, and there's no valid property to satisfy it). Logged clearly
  instead; relies on Channex's own retry backoff / the revision feed to keep
  re-surfacing it. Should only happen if a webhook arrives for a property
  whose channel connection couldn't legitimately have existed.
- Mixed-room-type single reservations: only the first resolved room-type
  group gets a BQ booking.
- `ack` removes a revision from the Channex *feed* (confirmed) - not
  confirmed to affect webhook redelivery specifically.

## Testing

**Automated** (`npm run test`, mocked - no live DB/Channex/BQ needed):
- `booking.service.test.ts` - 12 tests covering `processRevision()`: new
  booking (with `booking_type=OTA`/`booking_status=Hard`/Channex amount
  asserted), duplicate/already-acked idempotency, modification, cancellation,
  unmapped room/rate plan, unknown property, missing guest email, BQ failure.
- `booking.routes.test.ts` - 5 real HTTP-level tests (via `supertest`) of the
  webhook's authentication specifically: no header, wrong secret, no secret
  configured at all, correct secret, and confirming no `Authorization` header
  is required.

**Manual / live** (mint a token via `node scripts/mint-test-token.js
<propertyId>`, same as every other module):
```bash
# Should 401 until a gq_account_config row exists:
curl -X POST http://localhost:4000/api/gq/webhooks/channex \
  -H "Content-Type: application/json" -d '{"event":"booking"}'
```

**Live-verified end-to-end against real Channex/BQ data (2026-09-25).** Two
real Booking.com test reservations, made through an actual "Connect a
channel" flow, sat unacked in Channex's real revision feed - `processRevision()`
crashed on both, every time, until the bugs below were found and fixed by
testing against this real data (not synthetic payloads). After the fixes,
running `scripts/run-revision-feed.ts` for real created two real BQ bookings
(`bqOrderId 3733256741`/`bqBookingId 1955069520` and `bqOrderId
3492314977`/`bqBookingId 1337484294`), both then visible through `GET
/properties/:propertyId/bookings`.

**Real bugs found this way, fixed, not previously caught because every
earlier "live" test used synthetic data matching this integration's own
(wrong) assumptions about Channex's schema:**
1. **`revision_id` doesn't exist on a real revision's attributes.** Channex's
   docs and every piece of earlier research said revisions carry their own
   `revision_id` field - the real live API doesn't send one at all. The
   revision's actual identifier - what `GET/POST /booking_revisions/:id` and
   `ack` key off - is just the feed entry's own top-level `id`. Every call
   into `processRevision()` against real data crashed immediately
   (`cx_revision_id: undefined` - a Prisma error) until `revision.revision_id`
   was replaced with `revision.id` throughout `booking.service.ts` and the
   field was removed from `ChannexBookingRevisionAttributes`.
2. **`amount` is a numeric string** (e.g. `"181.15"`), not a number, on both
   a revision and each of its rooms. The old code multiplied it directly
   (`revision.amount * 100`) and summed it across rooms
   (`existing.amount += room.amount`) - the multiply happened to still work
   via JS's implicit string coercion, but the sum would have silently
   *string-concatenated* instead of added for a multi-room-of-the-same-type
   booking (e.g. `"160.00" + "160.00"` → `"160.00160.00"`, not `320`).
   Fixed with explicit `Number(...)` conversions, and switched the
   hardcoded `* 100` to the existing `toMinorUnits()` helper
   (`src/lib/currency.ts`) so 0-decimal currencies (JPY, the very currency
   one of these real test bookings used) don't get stored 100x too large.
3. **`arrival_date`/`departure_date` can be `null`.** A real Booking.com
   cancellation notice for one of these three revisions carried no stay
   dates at all - inserting it crashed with `Invalid Date`. Both
   `gq_ota_booking_revision` columns were changed to nullable (migration
   applied directly, `schema.prisma` updated to match), and every layer
   (repository, DTO, OpenAPI doc, frontend types/rendering) updated to
   treat them as `string | null`.

None of the 55 automated tests caught any of this, because the test
factories built their synthetic revisions to match the same wrong schema
assumptions as the code under test - a case of tests validating the
implementation's model of an external API rather than the API itself. The
test factories and fixtures have since been corrected to match the real
shape (`makeRevision()` in `booking.service.test.ts` no longer sets a
`revision_id` field, and `amount` is a string).

The webhook delivery path itself is still not live-tested end-to-end (no
real Channex webhook call has reached GQ - see the operational note below);
everything downstream of receiving a revision (mapping, idempotency, the
real BQ create/modify/cancel calls) now is, against real data.

**Operational gap, not a code bug:** if real OTA bookings aren't showing up
promptly, check whether `gq_account_config.webhook_url` actually points to a
real, publicly reachable HTTPS URL that's been registered with Channex via
`POST {CHANNEX_BASE_URL}/webhooks` - Channex's servers cannot reach
`localhost`. Until that's set up, `scripts/run-revision-feed.ts` is the
reliable path (it's an outbound GQ→Channex call, needs no inbound
connectivity) - just run it manually, or on a schedule, until a real webhook
URL exists.

### Creating test bookings

Channex has no simple, always-available way to push a test booking without
account-side setup:
- **Booking CRS API** (`POST /bookings`) needs the property to have the
  "Booking CRS App" installed first - it's beta/gated per-account; if it's
  not showing/enabling, that's on Channex's side (contact
  support@channex.io and ask them to enable Booking CRS App / beta access
  for the property), not something fixable from GQ's code.
- **Open Channel push-booking API** works without that gate, but needs a
  one-time "Open Channel" connection created in the Channex dashboard
  (Channels → Add New → type "Open Channel") first, which gets you a
  dedicated `api-key` from Channex for `POST
  /api/v1/channel_webhooks/open_channel/new_booking`.

Until either of those is set up, use the local simulation script instead -
it drives the exact same `processRevision()` the webhook and revision feed
use, with a synthetic (but schema-accurate) Channex revision payload, so it
still exercises GQ's real mapping/idempotency logic and makes real BQ API
calls:
```bash
npx ts-node scripts/simulate-booking-revision.ts new
# then, using the bookingId the "new" run printed:
npx ts-node scripts/simulate-booking-revision.ts modified <bookingId>
npx ts-node scripts/simulate-booking-revision.ts cancelled <bookingId>
```
The one thing it can't test is the final Channex-ack call (there's no real
revision on Channex's side to ack, so that call genuinely 404/422s) - the
script checks `gq_ota_booking`'s `bq_orderid`/`bq_bookingid` directly
afterward for the real ground truth, since `processRevision()`'s own
`outcome` can read `"blocked"` in that case even though the BQ booking was
created successfully.
